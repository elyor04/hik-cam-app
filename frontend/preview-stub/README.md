# Frontend-only preview stub

`frontend/wailsjs/` is normally auto-generated by `wails dev`/`wails build` (see the root
`.gitignore`) and requires compiling the Go backend, which pulls in `go-hikvision-sdk` -- a CGO
binding to Hikvision's proprietary HCNetSDK, vendored only for windows/linux amd64. On a machine
without that SDK vendored (e.g. macOS), the Go build fails and `wails dev` can't generate real
bindings.

This directory is the **hand-written stand-in**, so the UI can be rendered in a plain browser.

## Using it

```bash
npm run stub:install   # copies preview-stub/ -> wailsjs/
npm run dev
```

Then press **Connect** (any host/credentials -- they are ignored), then **Start** on Live View and
**Start** on the plate feed.

`stub:install` refuses to overwrite real generated bindings unless given `--force`, so running it by
accident on a machine that can build the backend cannot silently replace working bindings with demo
data. Delete `frontend/wailsjs/` before running `wails dev`/`wails build` for real.

## The live view is real video

This app exists to decode video, so a stub that only mocks bound methods would leave the one thing
worth looking at permanently blank. Instead the stub **synthesises an actual H.264 stream in the
browser**: a test pattern is drawn to a canvas, encoded with WebCodecs' `VideoEncoder` (Annex-B --
WebCodecs defaults H.264 to AVCC, which this pipeline would reject), framed in this app's own wire
format from `internal/wire`, and served through a `fetch` interception on one exact URL.

So `npm run dev` runs the genuine frontend path end to end: the wire parser, `VideoDecoder`, the
render loop, the frame-dropping policy, the stats and the phase state machine. The 600ms delay
before `stream:ready` is deliberate -- it reproduces the backend's codec sniff, so the `starting`
phase and the `IsStreamActive` catch-up are exercised rather than skipped.

What it does **not** cover is everything on the Go side of the boundary: `RealPlay`, the PS
demuxer, the broadcaster, the loopback HTTP server. Those only run against real hardware, and
`internal/wire`'s own tests are what cover them off-device.

## Keeping it in sync

Because it is hand-written, this stub goes stale every time a bound method is added, and nothing
notices on its own: Vite does not type-check, so `npm run dev` still starts and the failure appears
only when the affected control is used. The sibling `tarozi-post-app` repo let that run for six days
across 23 bound methods.

`npm run dev`, `npm run build` and `npm run stub:install` all run `scripts/check-stub-drift.mjs`,
which compares the `func (a *App) Xxx(` declarations in the root package against this stub's
exports. Run it alone with `npm run check:stub`.

It compares *names* only -- shapes are tsc's job, and tsc can only do that job if the export exists
at all. It is an error when `wailsjs/` currently holds the stub, and a warning otherwise, so a
production `wails build` on Windows never fails over a macOS-only convenience.

When you add a bound method: add it to `go/main/App.ts` here, then `npm run stub:install`.
